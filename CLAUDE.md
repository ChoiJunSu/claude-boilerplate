# Project: AI App Prototype (Claude API / Agent SDK)

This repo is a **personal prototyping boilerplate** for building apps on top of the Claude API and the Claude Agent SDK. Clone it, rename it, and start building.

---

## Workflow

New idea → ship in one sitting:

1. `/idea <one-line description>` — planner agent writes `docs/PRD.md` + `docs/ARCHITECTURE.md`
2. `/plan` — turn the PRD into a file-by-file implementation plan
3. `/build` — builder agent implements, committing as it goes
4. `/eval` — evaluator runs the prompt test set in `evals/`
5. `/ship` — shipper commits, pushes, and merges to the deploy branch (Git-based deploy)

Skip steps only if you know what you're doing. The point is to keep momentum.

This workflow is designed for the **mobile Claude app → Claude Code on the web** path. Start a new session on the repo from your phone and run `/idea` — everything from here on happens in the cloud sandbox and lands as commits.

---

## Default Models

Always use the latest Claude models. Do NOT fall back to older IDs.

| Role | Model | ID |
|---|---|---|
| Heavy reasoning, planning | Opus 4.6 | `claude-opus-4-6` |
| Default / agent loop | Sonnet 4.6 | `claude-sonnet-4-6` |
| Fast / cheap / classification | Haiku 4.5 | `claude-haiku-4-5-20251001` |

Hardcode these in code — no "configurable model" abstraction unless the app genuinely needs it.

## Claude API Rules (non-negotiable)

When you see `anthropic` or `@anthropic-ai/sdk` imports, the user-level **`claude-api` skill** applies. Follow it. In particular:

- **Prompt caching is required.** Put stable system prompts and tool definitions in a `cache_control: {type: "ephemeral"}` block. Never ship an agent loop without caching.
- **Tool use loop**: check `stop_reason`, handle `tool_use`, append `tool_result`, re-invoke until `end_turn`. No manual parsing of `<tool>` tags.
- **Structured output**: prefer tool use with a single "respond" tool over parsing free-form JSON.
- **Streaming**: use `client.messages.stream()` for user-facing UIs; use `.create()` for evals/batch.
- **Errors**: let 429s retry with backoff; don't swallow 400s.

For Agent SDK apps specifically: define tools as pydantic/zod schemas, keep the system prompt short, rely on the SDK's built-in loop rather than hand-rolling.

## Coding Principles

- **No speculative abstraction.** If you need it once, inline it. Three usages before a helper.
- **No defensive code at internal boundaries.** Trust your own functions. Validate at the edge (HTTP, CLI, LLM output).
- **No unrequested "improvements."** Fix the bug, ship the feature, stop.
- **No docstrings or comments on code you didn't change.** Only comment non-obvious logic.
- **Prefer editing existing files.** Create new files only when the structure actually demands it.
- **Small commits with clear messages.** One logical change per commit.

After a build session, run the user-level **`simplify` skill** manually to catch dead code and over-engineering.

## Environment (Claude Code on the web)

Primary target is **mobile Claude app → Claude Code on the web**. Every session runs in a fresh sandbox, so:

- **Secrets live in GitHub repo secrets / environment variables**, not in a committed `.env`. The sandbox receives them as env vars at session start.
- **`.env.example` is for local work only.** Copy it to `.env` if you're running outside the sandbox. `.env` is gitignored.
- **Dependencies install via `.claude/hooks/session-start.sh`**, which runs on session start in the sandbox. It detects `package.json`, `pyproject.toml`, `Cargo.toml`, `go.mod`, `Gemfile` and installs accordingly. Don't add your own `npm install` at the top of tasks — the hook handled it.
- **Never log secrets.** The transcript is visible in the mobile app history.

Required env vars:

- `ANTHROPIC_API_KEY` — always
- Deployment platform creds (e.g. `VERCEL_TOKEN`) — only if shipping via CLI rather than Git-based deploy

## Deployment Model

Default to **Git-based deploy**: connect the repo to Vercel (or Railway, Fly, Render, Cloudflare Pages — anything that deploys on push). `/ship` then means "merge to main and let the platform deploy." No CLI binaries assumed in the sandbox.

If Git-based deploy isn't an option for the target (e.g. Modal), `/ship` will install the CLI on demand and deploy from the sandbox.

## Directory Conventions

```
src/              # app code
evals/            # prompt eval sets for /eval
docs/
  PRD.md          # generated by /idea
  ARCHITECTURE.md # generated by /idea
  EVAL_REPORT.md  # generated by /eval
```

Keep the tree flat. No premature `utils/`, `lib/`, `helpers/` split.
